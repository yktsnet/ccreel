# Design Decisions

ccreel を作るあいだに下した設計判断と、技術の選定理由。README の Design Decisions は、ここから要点を抜いたものである。

## Tech Stack

| Layer | Technology | Reason |
|---|---|---|
| 本体 | Go（標準ライブラリだけ） | バイナリ1つで macOS と Linux の両方で動き、GNU と BSD のコマンドの差を避けられる |
| 選ぶ画面 | fzf | プレビュー・複数選択・絞り込みが使える。外部コマンドとして呼ぶ |
| 全文検索 | ripgrep | `rg` で候補のファイルを絞ってから読む。索引 DB を持たずに、手元の履歴（約1.4GB）で `find` が1秒かからない |
| 同期 | rsync + ssh | ハブに入れるものが要らない。差分だけを送れる |
| 配布 | Nix flake | 外部コマンドを PATH の後ろに足し、タイマーから起動されたときの最小限の PATH でも動く |

## J1. セッションをファイル単位の rsync `--update` で合わせる

- **選択肢**: ファイル単位の rsync `--update`（採用） / 差分の結合や索引を持つ同期（不採用）
- **決め手**: セッションの jsonl は追記しかされず、1本は1台の端末でしか書かれない。
  新しい方を残すだけで衝突が起きない。ハブ側では `--delete` を使わない
- **再検討の境界**: 同じセッションを2台で書く使い方（同じ UUID を両方で resume する）が日常になったとき

## J2. 常時動く VPS をセッションの置き場（ハブ）にし、一覧・検索・resume は手元の写しで行う

- **選択肢**: VPS は置き場だけにし、各端末が push・pull して手元にも写しを持つ（採用） / いまの端末どうしの rsync を続ける（不採用） / VPS で ccreel を動かし、一覧や検索を VPS に聞く（不採用） / Syncthing などの既製品で常時同期する（不採用）
- **決め手**: 端末どうしだと、相手がスリープしていると履歴が欠ける。`claude --resume` は手元に jsonl が無いと開けない。
  手元に写しがあれば、検索が速く、オフラインでも動き、Claude が skill から何度も呼んでも VPS まで行かずに済む。
  VPS にインストールするものは無く、ssh と rsync があればよい。既製品の同期は、push・pull を作り終えて動いていたので採らなかった。
  pull は直近30日（Claude Code の保持期間）に限る。全部を pull すると、手元で消えたセッションが pull のたびに戻ってくる。
  ハブは手元の保持期間より長い40日で消す。
  pick は開く前に pull する。タイマーで pull も回す端末は `--no-pull` で開き、ハブの応答を待たない。
- **再検討の境界**: 遅れや pull の待ちが気になるようになったとき（既製品の同期へ移る）、30日より古いセッションを探す場面が増えたとき、Claude Code の保持期間（`cleanupPeriodDays`）を変えたとき

## J3. 運ぶのはセッション本体の jsonl だけにする

- **選択肢**: 本体の jsonl だけを運ぶ（採用） / 付属物も運ぶ（不採用） / jsonl から resume に要らない行を削って運ぶ（不採用）
- **決め手**: resume に要るのは本体の jsonl だけで、サブエージェントの呼び出しと最終報告も本体に入っている。
  付属物は本体と同じくらいの容量を占める（手元の config dir の1つで約660MB）。
  行を削ると Claude Code のファイルを書き換えることになる。それで減る容量は15%ほどで、削ったファイルを開けるかを確かめる手間に見合わない
- **再検討の境界**: 別の端末でサブエージェントの中のやり取りを読み返す場面が増えたとき、または resume が付属物を読むようになったとき

## J4. push は手元の mirror と比べ、変わったものがあるときだけハブにつなぐ

- **選択肢**: ハブと同じ形の写し（mirror）を手元に持ち、更新日時を比べて変わったときだけ送る。タイマーで毎分呼ぶ（採用） / 毎回ハブにつなぎ、差分の判定を rsync に任せる（不採用） / Claude Code の `Stop` フックから push する（不採用）
- **決め手**: 毎回ハブにつなぐと、変わったものが無くても1回の push で ssh を3回つなぐ（ディレクトリの作成・rsync・古いものの削除）。
  手元で比べれば、変わったものが無い回は数ミリ秒で終わり、ハブにはつながない。そのため間隔を1分まで縮められる。
  問題になる遅れは、片方の端末で作業を終えてからもう片方で開くまでの時間で、5分おきでは直前の数往復が一覧に出ないことがあった。
  送れなかった変更は `.push-pending` に残して次の回に送り、古いものの削除は1日に1回にする。フックは、タイマーと仕組みが2つになるので足さない
- **再検討の境界**: 端末を閉じる直前の1分以内に更新した分が届かないことに困るようになったとき（`Stop` フックを足す）

## J5. config dir を分けずに1つの一覧に出し、resume はセッションのある config dir で開く

- **選択肢**: 全部の config dir のセッションを印なしで1つの一覧に出す（採用） / 起動した場所から config dir を1つ選び、その分だけを出す（不採用） / 1つの一覧に出し、どの config dir のものかの印を付ける（不採用）
- **決め手**: どの config dir で開いても、元の会話の続きになることは変わらない。resume は、そのセッションのある config dir を `CLAUDE_CONFIG_DIR` にして開く。
  リポの見分けは `@リポ` で足り、両方の config dir にセッションがあるリポはわずかだった。印は狭いペインで行の幅を取る
- **再検討の境界**: 同じリポの会話が複数の config dir に多く混ざり、どの config dir（ログインしているアカウント）で開くかを選ぶ前に知る必要が出たとき

## J6. ハブを置いたサーバーは pull せず、読むだけのコマンドがハブを直に読む

- **選択肢**: `CCREEL_HUB` が手元のディレクトリなら、読むだけのコマンドがハブも読む（採用） / サーバーでも pull する（不採用） / ハブを `CCREEL_CONFIG_DIRS` に足す（不採用）
- **決め手**: ハブを置いたサーバーは、スマホから Remote Control でつなぐ窓口を兼ねる。pull すると、他の端末の会話が窓口の `/resume` の一覧に混ざる。
  ハブを config dir として足すだけだと、サーバー自身の会話が手元とハブの両方に当たり、`show` が失敗し、一覧に2行ずつ出る。また、`~` の形の cwd では、ホームで起動した会話のリポを決められない。
  読むときに手元の方を優先し、cwd の `~` を戻せば、ハブのファイルには手を入れずに済む。ハブは40日ぶんを持つので、30日より古い会話も引ける
- **再検討の境界**: 窓口から他の端末の会話を resume したくなったとき

## 保留中の判断

決め切れていないもの。

- 全文検索を `rg -l` で絞る方式にするか、索引 DB を持つか：暫定は `rg -l`。手元の履歴（合わせて約1.4GB）で間に合っている
- SD カード程度のハブ向けに、rsync の `--append-verify` で追記分だけを書くか：いまは push のたびにハブがファイルを丸ごと書き直すので、作業中の大きなセッションでは書き込み量がかさむ
- 一覧の1行に出す「リポ」を、cwd の末尾から取るか、git のルートから取るか：いまは cwd の末尾から取り、worktree は元のリポの名前にする
